# Runbook: OpenCode Core

OpenCode 主服务 + Web 代理 + LAN 入口。

## Desired State

- `opencode.service` — 主服务，API 在 `127.0.0.1:4097`
- `opencode-4096-proxy.service` — Web 代理，`:4096`（注入 TTY 按钮）
- `opencode-18910-local.socket` + `opencode-18910-local.service` — LAN 代理，`:18910` → `:4096`；socket 监听 `0.0.0.0:18910`，service 使用 `/usr/lib/systemd/systemd-socket-proxyd 127.0.0.1:4096`
- `session-guard.service` — 会话守护，自动 memory sync + context save
- `opencode-rag-ingester.timer` + `.path` — 消费 lifecycle RAG 队列到本地召回索引
- `opencode-codegraph-warmup.timer` — 定时预热 CodeGraphContext/FalkorDB，避免 MCP 冷 socket 拒绝连接
- `opencode-health-watchdog.timer` — 定时探测 4097 API、内存、任务数和重复 MCP，必要时重启后端恢复 18910 稳定性
- `op-tasker-bridge.service` — 手机 Tasker/快捷按钮手动转交入口，监听 `:9814/task`，必须带设备码
- 配置: `~/.config/opencode/opencode.json`
- `oc` 命令直接连 `127.0.0.1:4097`，pin 在 `~/.local/share/opencode/openclaw-session`

## OP / Crush Auto Dispatch

- Use `agent-dispatch submit '<任务>'` as the automatic front door when the task can be handled by either OP or Crush.
- It scores both executors by task fit, live health, preference, and risk.
- OP is preferred for implementation, frontend, apps, workflows, and long project tasks.
- Crush is preferred for OP runtime repair, stopped-task diagnosis, review, verification, and short system checks.
- `agent-dispatch-watch.timer` checks active dispatches every minute. On failure or stall it hands off once to the other executor.
- If both OP and Crush fail, it writes a Codex-ready copy pack to `~/.local/state/agent-dispatch/failures/<dispatch-id>.md`.
- Do not add an OP↔Crush infinite retry loop. One handoff is the hard limit.

## Restart

```bash
# 全链路重启
systemctl --user restart opencode
sleep 3
systemctl --user restart opencode-4096-proxy opencode-18910-local

# 只重启 session-guard（不影响活跃会话）
systemctl --user restart session-guard
```

## Known Issues

- `opencode run` 只接受位置参数 `message`，不支持 `--prompt`
- agent 名区分大小写（`Bob` ≠ `bob`）
- `oc restart` 必须捕获 pinned session 和目录再恢复，不能创建替代 session
- `ttyd-8080.service` 依赖 `opencode.service` 但不能用 `Requires=`（手动重启会连带杀 ttyd）
- MCP 条目需 `type` + 数组 `command` + `enabled`，旧格式字符串 `command` 会导致启动失败
- 2026-06-25 诊断：OpenCode “记忆失效/智力下降”主要不是 MCP 不存在，而是 `opencode-lifecycle.py` 的 `classify()`/`terms()` 对短中文设备问题召回不足。例如“我开了无线调试了”“外面 5g”曾被判为 trivial 或提取成整块中文，导致 `contextChars=0`。已扩展 `adb/tailscale/无线调试/5g/公网/手机` 关键词和系统地图注入。
- agent-lifecycle 会把召回上下文拼进用户消息文本；post-learning 必须用 `strip_injected_context()` 清理，否则旧召回会污染任务日志和后续记忆。2026-06-25 已修成可清理任意位置的注入块。
- `session-guard.service` 可能 inactive；当前主路径是 OpenCode plugin `agent-lifecycle.mjs`，不是旧 `session-guard.sh`。不要只看 session-guard 判断记忆是否生效。
- 2026-06-25 全链路审计：`opencode-knowledge-maintainer.timer` 和 `opencode-capability-adapter.path` 曾因对应 `.service` 文件缺失而失败，导致地图/能力注册表不能自动更新。已补回 `opencode-knowledge-maintainer.service` 和 `opencode-capability-adapter.service`，两者都执行 `~/.local/bin/opencode-knowledge-maintainer.py`。
- Letta 归档不能作为唯一召回源：历史 passage 和新写入测试 passage 都显示 `embedding=null`，语义搜索可返回空或噪声结果。`opencode-lifecycle.py` 已改为 Letta 文本检索优先、关键词拆分兜底，语义搜索只作最后兜底。

- 2026-06-26 中断/卡住排查：OpenCode 服务未崩但任务多次需要“继续”时，优先检查 `systemctl --user status opencode` 的 Memory/Swap、`/proc/pressure/io`、`~/.local/state/opencode-lifecycle/events.jsonl` 是否出现密集 `knowledge_maintenance`，以及 OpenCode cgroup 内是否有长时间挂住的 `curl/find/fd` 子进程。本次根因是 path/maintainer 自触发维护风暴：`opencode-capability-adapter.path` 监听 generated runbooks，maintainer 写 runbook index 后反复触发；RAG ingester 重写队列也触发自身。已移除 generated runbooks 监听、给 maintainer 加 10 分钟节流、RAG 无变化不重写队列，并新增 `opencode-stuck-cleaner.timer` 清理低风险挂住读探针。
- 2026-06-26 18910 稳定性：18910 local proxy 通常不是瓶颈；若 18910 页面断流，先测 `127.0.0.1:4097/session` 延迟和 `opencode.service` 内 MCP 子进程套数。20 个 MCP 全 enabled 会让 OpenCode 为多个会话拉出多套 MCP，造成 4097 API 慢、内存顶到 `MemoryHigh`、swap 飙升。默认只启用核心 MCP：`fetch`、`codegraph`、`memory-engine`、`letta`、`context7`、`sys-info`、`haven`、`win`、`phone-connect`；Playwright/vision/firecrawl/khoj/tablet/ios/baidu/sqlite/ntfy/wechat/telegram 按需启用。`opencode-health-watchdog.timer` 会在 API 非 200、API >5s、内存 >4.5G、tasks >180 或重复 MCP 泄漏时重启后端。
- 2026-06-26 MCP 策略：新增 MCP 后 `opencode-knowledge-maintainer.py` 会按 name/command/url 自动分类并生成 `~/.ai-context/MCP_POLICY.{json,md}`。策略分为 `core` 和 `on_demand`：新 MCP 默认按需，除非加入 `CORE_MCPS` 并确认低成本、低风险。用 `opencode-mcp-policy list` 查看策略，用 `opencode-mcp-policy plan '<任务描述>'` 决定哪些 MCP 需要临时启用；`enable/disable` 会改 `opencode.json`，重启 OpenCode 后生效。OpenCode 命令：`/mcp-policy`、`/mcp-plan`、`/mcp-enable`、`/mcp-disable`。
- 2026-06-28 自主防卡死策略：OpenCode plugin `agent-lifecycle.mjs` 会拦截直接在 session 中启动长驻服务/容器的 bash 命令，包括 `podman/docker run`、`compose up`、后台 `npm dev/start`、`nohup`、`disown`。部署类任务必须落成 `~/.config/systemd/user/<name>.service` 并用 `systemctl --user enable --now <name>.service` 管理。`opencode-stuck-cleaner.timer` 会自动清理早于当前后端启动时间的 stale `opencode attach`，避免后端重启后旧 attach 继续占内存。

- 2026-06-28 Session 切换预加载实验：`opencode-4096-proxy` 支持用 `OPENCODE_SESSION_PRELOAD_ENABLED=1` 显式开启 `/__oc-session-preload.js` 和 `/session/<id>/message` 代理缓存，但默认必须关闭。实测 19MB/30MB/57MB/61MB 的大 message 包可被缓存加速，但浏览器端预加载会干扰 OpenCode 前端 session 内容显示，并且过度预热会把 4097 API 拖到 >5s 触发 health-watchdog。后续如要优化切换速度，应优先做只读 sidecar 摘要/增量索引，不要默认拦截 OpenCode 原生 message API。
